Plan: split the extension from the site, and start a library of fixes

Written 25 October 2026 by this site's agent, from Dinis Cruz's memo of the same day. A proposal for Dinis to accept, change or refuse; nothing here is started without his word. markdown.

Three repositories where there is one: the extension, with its own tests, releases and version; this site, which is the page and publishes the releases and the articles; and a library of fixes, generic and site-specific, each a small application with a policy, tests and a review, that a community can contribute to.

Why split

  • The website is the web page. It changes when the words change. The extension changes when the code changes. Today one version number covers both, which was right for a first release and will be wrong by the third.
  • The extension wants its own releases. A GitHub release per tag, with the zip and its hash as assets, is what a reader and a store expect. Today the zip is committed into the site.
  • Fixes are a third thing. They are data plus a small script under a policy, contributed by people who need not touch the extension, reviewed by a process of their own, and consumed by the extension as packs. They do not belong in either repository above.

The steps, in order

  1. Create the extension repository with its history

    git filter-repo --path extension/ --path tests/ --path admin/build/package.mjs --path admin/build/zip.js --path admin/build/icons.mjs on a fresh clone keeps every commit that touched those paths. The validator's extension checks move with it as scripts/validate.js; the site checks stay here. One commit, no code change.

  2. Give it its own pipeline

    On every push: validate, test (Playwright, as now). On a tag vX.Y.Z: build the zip, hash it, create the GitHub release with both as assets. The tag job from the hub's pipeline applies unchanged; the deploy job goes.

  3. Teach this site to serve a release it did not build

    A small script, admin/build/fetch-release.mjs <version>, downloads the zip and the hash from the extension's release, verifies the hash, and writes them into releases/ with a releases/current.json naming the version. The validator checks the hash against the file and the site's pages against current.json instead of against extension/. The install page says "extension vX.Y.Z, site vA.B.C".

  4. Remove extension/ and tests/ from this repository

    After the extension repository has had one green release and this site has served it. The README here points at the extension repository; the source page lists its files by link.

  5. Start the fixes repository with the examples

    The seven playground examples become the first seven fixes, in the folder shape below, with tests on the fixtures already written. The README template, the review template and the CI are written once and copied.

  6. Teach the extension to import a pack

    A pack is { format: "fix-the-page/pack", version, name, fixes: [experiments...] }, the experiments export with a name and, later, a signature. Import shows every fix and its policy before anything is kept. Then: run kept fixes at load on granted sites, under their policies, which needs the sandbox to run without the playground open (an offscreen document, or the sandbox hosted by the options page while it is open; to be designed and measured).

  7. Ask the hub to link to both

    The hub is read-only to this agent; the request goes to Dinis or to the hub's agent.

Generic fixes and site-specific fixes

The same shape, told apart by match, and by what they are allowed to assume:

GenericSite-specific
Match*://*/* or https://*/*one origin, or a path under it
Folderfixes/generic/<slug>/fixes/<host>/<slug>/
May assumeonly the platform: CSS, the title, headingsthe site's markup, named selectors; a site's own page API where it has one
Honesty label"best effort" where it guesses, as the newsroom's generic reading mode does"as of" a date, because markup changes; the test fixture is a snapshot of the site's markup
Capabilities, typicallycss.add, title.*dom.count, dom.hide, dom.setText, with a selector allowlist in the policy
Examples todaybigger text; prefix the title with the host; hide sticky bars (best effort)hide one element; rename a heading

A site-specific fix should carry selectors in its policy: the exact selectors it may name. Then a reviewer reads five lines and knows the whole reach of the fix, and the gate refuses any other selector at run time.

Every fix a small application

fixes/example.com/hide-cookie-banner/
  fix.json     { "name", "match", "policy": { capabilities, limits, selectors }, "author", "version", "licence", "asOf" }
  fix.js       the script
  README.md    what it does, for a reader; must name the same capabilities as the policy
  tests/
    page.html  a fixture: the site's markup, trimmed, as of the date in fix.json
    expect.json  what must be true after the fix runs: hidden selectors, title, text
  REVIEW.md    reviewer, date, the delta they computed, what they ran; later a signature

CI on a pull request: the lint (calls ⊆ policy, no banned names, no unused grants); the tests under the sandbox harness in tests/fixtures/sandbox-host.html; README names ⊆ policy and policy ⊆ README names; fix.json validates as an experiment. A reviewing agent gets a skill that says: read the three files, compute the delta both ways, run the tests, write REVIEW.md. Human review stays for anything site-specific that names a selector on a page with money or data behind it. The barrier on the repository is a boundary; the barrier on the running fix is the runtime's and does not depend on the review having been right.

Opening it up

  • Contribution is a pull request with one folder. The template repository gives the shape; CI gives the first review; a maintainer merges.
  • Packs are the unit of distribution. A pack per site ("example.com, 4 fixes") or per theme ("reading, 3 fixes"), built by CI from merged fixes, published as a release of the fixes repository and, when the vault route is ready, from an sgit vault with a read key.
  • Signing comes from pki.sgit.ai. A maintainer key signs each pack; an author key may sign each fix. The extension shows who signed, and refuses a pack changed after signing. proposed
  • Kept fixes are the roadmap. The original article's argument: the fixes people keep are the best brief a site will get. A count of kept fixes, in the reader's own record and sent only if they choose, would tell site owners which primitives to publish.

Decisions for Dinis

  1. The names of the two new repositories (see the note above).
  2. Whether this site keeps serving the zip (recommended: yes, fetched and verified from the extension's release) or links to the GitHub release only.
  3. Whether saved fixes should ever run without the playground open, and if so on which barrier: granted sites only, under their policies, with the same Undo.
  4. Whether selectors should be required in the policy of every site-specific fix (recommended: yes).
  5. The licence for contributed fixes (the family's default is Apache 2.0 for code, CC BY 4.0 for words).
