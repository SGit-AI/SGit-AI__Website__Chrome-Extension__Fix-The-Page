Script Behaviour Policies: a behaviour policy for a line of JavaScript

By Dinis Cruz, written up by this site's agent · 25 October 2026 · published · markdown twin

A line of JavaScript on a page can do everything the page can: read every field, every cookie the page can see, send it anywhere, rewrite anything. A fix that sets the tab's title has the same reach as one that empties your inbox. That is ridiculous, and it is normal. The Agent Behaviour Policy writes down what an agent can reach, what you asked of it, the gap, and what stands in the way; the Process Behaviour Policy did the same for a process. This article does it for a script: the Script Behaviour Policy, a short document that says a script may set the title and nothing else, checked when the script is read and enforced while it runs, by something the script cannot reach. The first one is running in Fix the Page's playground. built

In short

  • A script's grant is the whole page. Whatever a page can do, any script on it can do: the DOM, the network, storage, navigation, the clipboard on a click. There is no smaller unit of trust in the platform.
  • The mandate is almost always one line. "Set the title." "Hide that banner." "Make the text bigger." The gap between the two is the problem, and it is the same gap the ABP was built to write down.
  • A Script Behaviour Policy is a list of capabilities and limits. title.set, and at most a hundred calls in five seconds. Eight capabilities exist today. A name not in the vocabulary cannot be granted and will not be performed.
  • Static review is the lint, the reviewer and the CI. Compare what the script calls with what the policy grants; refuse names that have no place in a fix; keep the policy as tight as the script. Advice, with a barrier of the expectation kind, until CI refuses the merge.
  • Runtime enforcement is a realm with nothing in it. The script runs in a sandboxed page with an opaque origin and no network. It sees one object, page, whose methods post messages. The playground, in another realm, checks every message against the policy; the engine on the page checks the arguments again and keeps an undo log. The script cannot reach either of them.
  • "A control bounds a grant only if it is enforced by something the grant does not include." That is the ABP's test, and it is the design rule here: the gate is never in the script's realm.
  • Every fix becomes a small application. A script, its policy, a README that says the same thing, tests on a fixture page, a review. That is the shape a community library needs, and the shape a reviewing agent can be given as a skill.

The grant of a script is the page

Chrome's own documentation on content scripts says they "live in an isolated world" where "JavaScript variables in an extension's content scripts are not visible to the host page", while content scripts and the host page "share access to the page's DOM". That isolation protects the extension from the page and the page from the extension's variables. It does nothing to narrow what a script may do to the page. Here is the grant, measured the way the ABP measures one, for a script that runs with the page's DOM:

Seven rows; the mandate touches one of them, partially. Every other row is excess, and in the usual arrangement (a bookmarklet, a userscript manager, an extension with host permissions) the barrier on every row is the first kind: none. The reviewer's "I read it and it only sets the title" is the second kind, an expectation. The ABP's words: "a rule in prose, enforced by nobody".

From ABP, through PBP, to SBP

The Agent Behaviour Policy is four objects: "the mandate (elicited), the grant (measured), the delta (derived), the barrier (recorded per capability, from one of four kinds)". The Process Behaviour Policy applied them to a process, where the kernel can make almost every line a boundary, and added two rules that transfer: layers can only narrow ("the effective policy is the intersection"), and "a business rule is only a Boundary if it is enforced in a different process from the one it constrains". For a script, the different process is a different realm.

No layer can grant what the one above refused. A policy cannot ask for network.send, because L1 has no such verb. A run cannot reach a tab the popup was not opened on, because L0 has no host permission for it. This is the PBP's intersection rule, and it is also why the vocabulary grows slowly: every verb added to L1 is a verb every policy could ask for.

Static enforcement: the review

Three readers, in order of cost.

  1. The lint, as you type. It finds every page.x.y( in the script and compares the list with the policy. A call the policy does not grant: not ready to run. A grant the script does not use: untick it, so the policy is as tight as the script. A name from the banned list (window, document, fetch, eval, chrome, constructor and thirty more): not ready to run, with the line number. It is a regex, not a parser; it says so.
  2. A reviewer, human or agent, with the policy in one hand and the README in the other. The question is not "is this code safe" (the runtime answers that) but "does this fix do what it says, and no more than its policy, and is the policy as small as the job". For an agent that is a skill: read the three files, compute the delta, say it in one paragraph.
  3. CI, for a library. The same lint as a gate; the tests under the sandbox harness; a check that every capability the README names is in the policy and every capability in the policy is named in the README. The plan has the shape of the repository.

  1. The playground builds the policy from the ticked boxes and runs the lint. Not clean, no run.
  2. It posts the script, the capability list and the limits to the sandbox iframe. Chrome's manifest reference says a sandboxed page is "served in a sandboxed unique origin" and "won't have access to extension APIs"; it "may communicate with them using postMessage()". Ours also has a Content Security Policy of sandbox allow-scripts; script-src 'self' 'unsafe-eval'; connect-src 'none' and nothing else allowed, which the validator checks on every build.
  3. The sandbox makes a page object whose methods are the granted capabilities and nothing else, builds the script into a function with the usual globals shadowed, and runs it under a timer.
  4. Each call becomes a message. The playground is the gate: checkCall(policy, call) is a pure function (tested in Node) that refuses anything not granted, any wrong argument shape, any selector outside an allowlist if one is set. Refusals are written in the run log, in words.
  5. Allowed calls go to the engine on the tab, which checks the arguments again, applies the effect, and records it. Undo reverses a run's effects in reverse order: hidden elements shown, text restored, stylesheets removed, the title released.
  6. When the script ends, or the timer fires, the run is closed and later messages for it are refused.

The same message gate meets a message the script did not send through page. The test suite escapes the shadowing on purpose, through the async function constructor, and reports what it finds: the sandbox's own window, with no extension API, no page, and a fetch the CSP refuses.

The worked example

The fix Dinis asked for first, as a policy and a script:

{
  "policy": "fix-the-page/sbp",
  "version": 1,
  "capabilities": ["title.set"],
  "limits": { "calls": 100, "ms": 5000 }
}

// the script: the body of an async function; it sees page and log, nothing else
await page.title.set('Ops dashboard');

Change the script to await page.css.add('body { display: none }') and the lint says: the script calls css.add but the policy does not grant it. Tick nothing and press Run anyway through the test hook, and the gate says: refused page.css.add("body { display: none }"): css.add is not in the policy. The page is unchanged. That is the whole idea in two lines of log.

Every fix is a small application

For a library that strangers contribute to, the policy is what makes review possible at all. The proposed shape of one fix, generic or site-specific:

fixes/example.com/hide-cookie-banner/   or  fixes/generic/bigger-text/
  fix.json      name, match, the policy, author, version, licence
  fix.js        the script, the body of an async function over page and log
  README.md     what it does, in words a reader can compare with the policy
  tests/        a fixture page and what the fix must change, run under the sandbox harness
  REVIEW.md     who read it, the delta they computed, when; later, a signature

CI runs the lint, runs the tests, compares README with policy, and refuses the merge otherwise. A reviewing agent gets the same three files and a skill that says what to look for. The barrier on the repository is a boundary; the barrier on the running fix is the runtime's, as above, and it does not depend on the reviewer having been right. Later, the policy and the script are hashed together and signed with a key the pki.sgit.ai register vouches for, as the newsroom's Pen signs notes, and a fix changed after signing fails to load.

What this does not claim

  • Not a boundary against a malicious extension. The gate and the engine are our code, inside the extension. A reader who installs the extension trusts the extension; the policy bounds the scripts, not the thing that runs them. The source is public so that trust can be checked.
  • A bug in a capability is a bug in the boundary. If dom.setText could be made to run markup, the policy would still say dom.setText. The vocabulary is small so that each verb can be read, bounded and tested.
  • The lint is advice. It reads a regex's view of the script. The gate does not depend on it.
  • A tight synchronous loop is not stopped. The timer fires only when the script yields. The sandbox's thread freezes; the page it was going to fix does not. A gap, recorded here as the ABP's gaps register would.
  • A policy describes and does not judge. css.add is harmless on a newspaper and can hide the pay button on a shop. Whether a fix is safe is a property of the site it runs on and the person who kept it, not of its policy. The ABP says it of deployments; it is true of pages.
  • One realm, one run. Saved experiments run when you press Run, with the playground open. Running them on their own, at load, on a granted site, is specified and not built.
  • Eight verbs. A start, not a library.

Where this comes from

A memo from Dinis Cruz on 25 October 2026, after the first install: start with the extension installed from a clone; the first easy fix is document.title; then site-specific fixes, a playground to prototype them and keep them, a community that contributes them, each one a small application with a review and security checks, and a behaviour policy for scripts that limits what a script can do, enforced both by static analysis and at run time. The model is the Agent Behaviour Policy at abp.sgit.ai and riskmandate.ai ("the mandate, the grant, the delta and the barrier", the four barrier kinds, "a control bounds a grant only if it is enforced by something the grant does not include"), and the Process Behaviour Policy in cli.sgit.ai's sealed vault keys design pack (layers that only narrow; who enforces decides the barrier kind). The idea of fixes as one-line calls on primitives is the newsroom's Fix the page yourself. Chrome facts are quoted from the sandbox manifest reference and the content scripts page, fetched on 25 October 2026. The code is in extension/: sbp.js, sandbox.js, playground.js and the capability half of engine.js, with the tests in tests/.

For an agent. A Script Behaviour Policy is { "policy": "fix-the-page/sbp", "version": 1, "capabilities": [...], "limits": { "calls": n, "ms": n }, "selectors": [...]? }. The capability vocabulary is the eight names in extension/sbp.js. To review a fix: compute the calls the script makes (page.x.y(), compare with the policy, name the delta both ways, check the README names the same capabilities, run the tests under tests/fixtures/sandbox-host.html. The gate is checkCall(policy, call); the lint is lintScript(script, policy); both are pure and run in Node.
